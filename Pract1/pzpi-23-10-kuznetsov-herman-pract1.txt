3 ОПИС ВИКОНАНОЇ РОБОТИ
      3.1 Загальні відомості про шаблони проєктування
      У сучасній інженерії програмного забезпечення шаблони проєктування розглядаються як апробовані та типізовані способи вирішення повторюваних задач у процесі проєктування архітектури. Використання шаблонів дозволяє забезпечити високий рівень абстракції, що сприяє створенню гнучких, масштабованих та легких у супроводі програмних систем. Шаблони проєктування класифікуються за трьома основними категоріями: твірні (creational), структурні (structural) та поведінкові (behavioral).
      Поведінкові шаблони, до яких належить «Відвідувач», фокусуються на алгоритмах та розподілі відповідальності між об'єктами. Вони описують не лише самі класи чи об'єкти, а й складні типи взаємодії між ними. Застосування таких підходів мінімізує зв’язність (coupling) компонентів системи, що є критично важливим при розробці складних корпоративних систем або програмних комплексів з тривалим життєвим циклом.
      3.2 Опис обраного патерна
      Шаблон проєктування «Відвідувач» (Visitor) — це поведінковий паттерн, що дозволяє відокремити алгоритми від об'єктів, на яких вони оперують. Основна ідеологія патерна полягає у забезпеченні можливості додавання нових операцій до існуючих структур об’єктів без необхідності модифікації їхнього вихідного коду. Це безпосередньо реалізує один із ключових принципів об’єктно-орієнтованого проєктування — принцип відкритості/закритості (Open/Closed Principle).
      
      Ключовою особливістю «Відвідувача» є використання механізму подвійної диспетчеризації (double dispatch). У мовах програмування, що підтримують лише одинарну диспетчеризацію (наприклад, C++ або Java), вибір методу для виконання залежить лише від імені операції та типу об’єкта, який її викликає. Патерн «Відвідувач» дозволяє обійти це обмеження, забезпечуючи вибір конкретної реалізації операції залежно від типів двох об’єктів: безпосередньо «Відвідувача» та «Елемента», який він опрацьовує. Це робить систему надзвичайно гнучкою при необхідності виконання різнотипних операцій над складною ієрархією об’єктів (наприклад, деревом синтаксичного аналізу або структурою компонентів обладнання).
      3.3 Структура шаблона
      Архітектура патерна «Відвідувач» базується на взаємодії таких компонентів:
      1. Visitor (Інтерфейс відвідувача): Визначає набір методів visit, кожен з яких призначений для роботи з конкретним класом елементів. Кількість методів в інтерфейсі відповідає кількості типів об’єктів у структурі, яку необхідно обійти.
      2. ConcreteVisitor (Конкретний відвідувач): Реалізує конкретну логіку або операцію, що має бути виконана над елементами. Різні конкретні відвідувачі можуть реалізовувати абсолютно різні функції (наприклад, один для експорту даних, інший для збору статистики), не впливаючи на класи самих даних.
      3. Element (Інтерфейс елемента): Описує базовий інтерфейс для всіх об’єктів структури. Головним методом є accept(Visitor*), який слугує точкою входу для відвідувача.
      4. ConcreteElement (Конкретний елемент): Реалізує метод accept. Усередині цього методу викликається відповідний метод visit переданого об'єкта-відвідувача, при цьому елемент передає самого себе (this) як аргумент.
      5. ObjectStructure (Структура об'єктів): Клас або сукупність об’єктів (наприклад, список, дерево або колекція), що надає інтерфейс для обходу своїх елементів відвідувачем.
      Дана структура забезпечує чітке розділення відповідальності: класи елементів відповідають лише за зберігання даних та представлення предметної області, тоді як класи відвідувачів інкапсулюють усю допоміжну логіку обробки цих даних.
UML-діаграма з поясненнями
      
      Рисунок 3.1 – UML-діаграма структури патерну Visitor
Представлена UML-діаграма відображає архітектурну структуру поведінкового шаблону проєктування «Відвідувач» (Visitor) та демонструє взаємозв’язки між його основними компонентами.
      1. Компоненти інтерфейсів (Abstractions):
      Visitor: Абстрактний інтерфейс, що визначає контракт для об’єктів-відвідувачів. Він містить методи visitConcreteElementA(elementA) та visitConcreteElementB(elementB). Кожен метод перевантажений для роботи з конкретним типом елемента, що забезпечує можливість виконання специфічних операцій над різними класами в ієрархії.
      Element: Базовий інтерфейс для ієрархії об’єктів, що підлягають обробці. Ключовим елементом є чисто віртуальний метод accept(visitor), який ініціалізує механізм взаємодії з алгоритмом відвідувача.
      2. Конкретні реалізації (Concrete Implementations):
      ConcreteVisitor: Реалізує методи інтерфейсу Visitor. У цих класах зосереджена прикладна логіка (алгоритм), яка виконується над елементами. Кожен конкретний відвідувач може реалізовувати різну поведінку (наприклад, один — для аудиту, інший — для експорту даних).
      ConcreteElementA / ConcreteElementB: Реалізують інтерфейс Element. В архітектурі вони виконують роль приймачів відвідувача. Метод accept у цих класах реалізований за принципом: visitor.visitConcreteElement(this), що забезпечує передачу контексту (самого об’єкта) до алгоритму.
      3. Типи зв’язків на діаграмі:
      Реалізація (Realization/Inheritance): Позначена пунктирними лініями з незафарбованими стрілками від конкретних класів до інтерфейсів (Visitor та Element). Це свідчить про дотримання принципу інверсії залежностей.
      Залежність (Dependency): Позначена пунктирними стрілками. Visitor залежить від класів ConcreteElement, оскільки використовує їх як параметри методів. Водночас Element залежить від інтерфейсу Visitor.
      Асоціація (Association): Клієнтський код (Client) має асоціативний зв'язок з інтерфейсами елементів та відвідувача, що дозволяє йому оперувати абстракціями, не прив’язуючись до конкретних реалізацій.
     Дана UML-структура демонструє застосування принципу подвійної диспетчеризації. Завдяки такому компонуванню ми отримуємо систему, де додавання нових операцій (нових відвідувачів) не потребує зміни коду вже існуючих елементів, що значно полегшує підтримку та розширення програмного продукту.
3.4 Реалізація шаблона (патерна)
      Опис реалізації мовою програмування С++
      Основні етапи:
      1. Створення базових інтерфейсів
      На початковому етапі розробки проєкту формується абстрактний фундамент системи, що базується на принципі подвійної диспетчеризації:
      Оголошується абстрактний базовий клас Visitor (або ShapeVisitor/AccountVisitor), який виконує роль інтерфейсу для всіх майбутніх операцій. Він визначає набір чисто віртуальних методів visit, кожен з яких перевантажений для роботи з конкретним типом елемента. Це створює жорсткий контракт, який гарантує, що будь-який новий алгоритм буде сумісний з усіма існуючими компонентами системи.
      Створюється абстрактний клас Element (Shape/BankAccount/DocumentNode), від якого успадковуються всі майбутні об'єкти структури. Його головна задача — визначити метод accept(Visitor*), який слугує "шлюзом" для зовнішніх відвідувачів.
      Реалізуються класи конкретних елементів. У базовій концепції це фігури (Circle, Rectangle), у прикладній — банківські рахунки, а в архітектурній — вузли документа (Text, Image). Кожен із цих класів містить власну логіку збереження даних. Наприклад, метод accept у класі Circle лише викликає visitor->visitCircle(this), передаючи самого себе для обробки. Це дозволяє повністю ізолювати структуру даних від алгоритмів (Див. додаток В.1).
      2. Реалізація конкретних класів
      На цьому етапі розробляється безпосередня функціональність, яка інкапсулюється в окремих класах-відвідувачах, що дозволяє динамічно змінювати поведінку системи:
      Реалізовано класи конкретних відвідувачів для різних прикладних задач. Наприклад, у банківській системі відвідувач InterestVisitor відповідає за нарахування відсотків, а ReportVisitor — за формування консольної звітності.
      Головна логіка обробки даних зосереджена в методах visit(). Отримавши доступ до об'єкта, відвідувач аналізує його стан через публічний інтерфейс (гетери) та виконує необхідні дії. В архітектурній реалізації це дозволяє виконувати складні операції, такі як валідація вмісту документа або його експорт у формат XML. Такий підхід дозволяє концентрувати споріднену логіку в одному місці (класі відвідувача), а не розпорошувати її по всій ієрархії елементів (Див. додаток В.2).
      3. Демонстрація використання
      У клієнтській частині моделюється життєвий цикл системи та взаємодія об'єктів:
      Спочатку створюється структура об'єктів (Object Structure) — зазвичай це контейнер (наприклад, std::vector), що містить вказівники на базовий тип елемента. Це дозволяє зберігати різнорідні об'єкти (коло та квадрат, або текст та зображення) в одній колекції.
      Створюється об'єкт конкретного відвідувача, після чого запускається цикл обходу структури, де для кожного елемента викликається метод accept.
      Демонстрація в архітектурному прикладі (Додаток В.3) показує найвищий рівень гнучкості: використання розумних вказівників (std::unique_ptr) та реалізацію складних відвідувачів, як-от XmlExportVisitor та ValidationVisitor. Клієнт спочатку "проганяє" відвідувача-експортера для отримання XML-коду, а потім того ж самого списку об'єктів — відвідувача-валідатора для перевірки цілісності даних. Ця демонстрація підтверджує, що додавання нової поведінки (наприклад, експорту в JSON або PDF) досягається лише створенням нового класу-відвідувача, без жодного втручання в програмний код самих елементів документа (Див. додаток В.3).

4 ВИСНОВКИ
У ході виконання практичної роботи було проведено всебічне дослідження та програмну реалізацію поведінкового шаблону проєктування Visitor, що дозволило підтвердити його високу ефективність у контексті розширення функціональних можливостей програмних систем без внесення змін до їхньої базової архітектури. Під час аналізу було встановлено, що головна архітектурна перевага даного патерна полягає у забезпеченні повної відповідності принципу відкритості/закритості, оскільки додавання нових операцій над існуючими об'єктами здійснюється шляхом створення нових класів-відвідувачів, що не потребує перекомпіляції ієрархії елементів. Практична реалізація механізму подвійної диспетчеризації продемонструвала здатність системи динамічно обирати необхідний алгоритм обробки у рантаймі, що значно підвищує гнучкість управління складними структурами об'єктів. Окрему увагу було приділено розподілу обов'язків, де класи елементів інкапсулюють виключно структуру даних, а класи відвідувачів — логіку їхньої обробки, що сприяє покращенню чистоти коду та спрощенню подальшої підтримки програмного продукту. Розроблені приклади різного рівня складності, від базових геометричних фігур до складних документо-орієнтованих систем, наочно ілюструють масштабованість шаблону та його придатність для вирішення широкого спектра інженерних задач. Зроблено висновок, що попри певне ускладнення при зміні структури самих елементів, паттерн Visitor є незамінним інструментом для побудови адаптивних систем зі стабільною структурою даних та динамічно змінними вимогами до методів їхньої обробки. Завдання роботи виконано в повному обсязі, а отримані результати засвідчують глибоке засвоєння принципів об'єктно-орієнтованого проєктування.

#include <iostream>
#include <vector>
#include <memory>

// Випереджальне оголошення
class Circle;
class Rectangle;

// Абстрактний відвідувач
class ShapeVisitor {
public:
    virtual ~ShapeVisitor() = default;
    virtual void visitCircle(Circle* c) = 0;
    virtual void visitRectangle(Rectangle* r) = 0;
};

// Базовий клас елемента
class Shape {
public:
    virtual ~Shape() = default;
    virtual void accept(ShapeVisitor* visitor) = 0;
};

// Конкретний елемент: Коло
class Circle : public Shape {
public:
    double radius;
    Circle(double r) : radius(r) {}
    void accept(ShapeVisitor* visitor) override { visitor->visitCircle(this); }
};

// Конкретний елемент: Прямокутник
class Rectangle : public Shape {
public:
    double width, height;
    Rectangle(double w, double h) : width(w), height(h) {}
    void accept(ShapeVisitor* visitor) override { visitor->visitRectangle(this); }
};

// Конкретний відвідувач: Обчислення площі
class AreaVisitor : public ShapeVisitor {
public:
    void visitCircle(Circle* c) override {
        std::cout << "Площа кола: " << 3.14159 * c->radius * c->radius << std::endl;
    }
    void visitRectangle(Rectangle* r) override {
        std::cout << "Площа прямокутника: " << r->width * r->height << std::endl;
    }
};

int main() {
    setlocale(LC_ALL, "Ukrainian");
    std::vector<std::unique_ptr<Shape>> shapes;
    shapes.push_back(std::make_unique<Circle>(5.0));
    shapes.push_back(std::make_unique<Rectangle>(4.0, 6.0));

    AreaVisitor areaCalc;
    for (const auto& s : shapes) {
        s->accept(&areaCalc);
    }
    return 0;
}

#include <iostream>
#include <string>
#include <vector>

class SavingsAccount;
class CheckingAccount;

// Інтерфейс відвідувача для банківських операцій
class AccountVisitor {
public:
    virtual void visit(SavingsAccount& acc) = 0;
    virtual void visit(CheckingAccount& acc) = 0;
    virtual ~AccountVisitor() = default;
};

// Базовий клас банківського рахунку
class BankAccount {
protected:
    double balance;
public:
    BankAccount(double b) : balance(b) {}
    virtual void accept(AccountVisitor& visitor) = 0;
    double getBalance() const { return balance; }
    void setBalance(double b) { balance = b; }
    virtual ~BankAccount() = default;
};

class SavingsAccount : public BankAccount {
public:
    SavingsAccount(double b) : BankAccount(b) {}
    void accept(AccountVisitor& visitor) override { visitor.visit(*this); }
};

class CheckingAccount : public BankAccount {
public:
    CheckingAccount(double b) : BankAccount(b) {}
    void accept(AccountVisitor& visitor) override { visitor.visit(*this); }
};

// Конкретний відвідувач: Нарахування відсотків
class InterestVisitor : public AccountVisitor {
public:
    void visit(SavingsAccount& acc) override {
        acc.setBalance(acc.getBalance() * 1.05); // +5%
    }
    void visit(CheckingAccount& acc) override {
        acc.setBalance(acc.getBalance() * 1.01); // +1%
    }
};

// Конкретний відвідувач: Генерація звіту
class ReportVisitor : public AccountVisitor {
public:
    void visit(SavingsAccount& acc) override {
        std::cout << "Ощадний рахунок. Баланс: " << acc.getBalance() << " грн." << std::endl;
    }
    void visit(CheckingAccount& acc) override {
        std::cout << "Поточний рахунок. Баланс: " << acc.getBalance() << " грн." << std::endl;
    }
};

int main() {
    setlocale(LC_ALL, "Ukrainian");
    std::vector<BankAccount*> bank;
    bank.push_back(new SavingsAccount(1000));
    bank.push_back(new CheckingAccount(500));

    InterestVisitor interest;
    ReportVisitor report;

    for (auto acc : bank) acc->accept(interest);
    for (auto acc : bank) acc->accept(report);

    for (auto acc : bank) delete acc;
    return 0;
}

#include <iostream>
#include <vector>
#include <memory>
#include <string>

class TextElement;
class ImageElement;
class TableElement;

// Абстракція відвідувача з повною ієрархією компонентів документа
class DocumentVisitor {
public:
    virtual void visitText(const TextElement& el) = 0;
    virtual void visitImage(const ImageElement& el) = 0;
    virtual void visitTable(const TableElement& el) = 0;
    virtual ~DocumentVisitor() = default;
};

// Інтерфейс вузла документа
class DocumentNode {
public:
    virtual void accept(DocumentVisitor& v) const = 0;
    virtual ~DocumentNode() = default;
};

class TextElement : public DocumentNode {
    std::string content;
public:
    explicit TextElement(std::string c) : content(std::move(c)) {}
    void accept(DocumentVisitor& v) const override { v.visitText(*this); }
    std::string getText() const { return content; }
};

class ImageElement : public DocumentNode {
    std::string path;
public:
    explicit ImageElement(std::string p) : path(std::move(p)) {}
    void accept(DocumentVisitor& v) const override { v.visitImage(*this); }
    std::string getPath() const { return path; }
};

class TableElement : public DocumentNode {
    int rows, cols;
public:
    TableElement(int r, int c) : rows(r), cols(c) {}
    void accept(DocumentVisitor& v) const override { v.visitTable(*this); }
    std::pair<int, int> getSize() const { return { rows, cols }; }
};

// Відвідувач: Експорт у формат XML
class XmlExportVisitor : public DocumentVisitor {
public:
    void visitText(const TextElement& el) override {
        std::cout << "<text>" << el.getText() << "</text>\n";
    }
    void visitImage(const ImageElement& el) override {
        std::cout << "<image path=\"" << el.getPath() << "\"/>\n";
    }
    void visitTable(const TableElement& el) override {
        auto size = el.getSize();
        std::cout << "<table rows=\"" << size.first << "\" cols=\"" << size.second << "\"/>\n";
    }
};

// Відвідувач: Валідатор цілісності даних
class ValidationVisitor : public DocumentVisitor {
    bool all_valid = true;
public:
    void visitText(const TextElement& el) override {
        if (el.getText().empty()) all_valid = false;
    }
    void visitImage(const ImageElement& el) override {
        if (el.getPath().empty()) all_valid = false;
    }
    void visitTable(const TableElement& el) override {
        if (el.getSize().first <= 0) all_valid = false;
    }
    bool result() const { return all_valid; }
};

int main() {
    setlocale(LC_ALL, "Ukrainian");
    std::vector<std::unique_ptr<DocumentNode>> document;
    document.push_back(std::make_unique<TextElement>("Заголовок звіту"));
    document.push_back(std::make_unique<ImageElement>("logo.png"));
    document.push_back(std::make_unique<TableElement>(10, 3));

    XmlExportVisitor xmlExporter;
    std::cout << "--- XML Експорт ---\n";
    for (const auto& node : document) {
        node->accept(xmlExporter);
    }

    ValidationVisitor validator;
    for (const auto& node : document) {
        node->accept(validator);
    }
    std::cout << "Статус валідації: " << (validator.result() ? "Коректно" : "Помилка") << std::endl;

    return 0;
}
