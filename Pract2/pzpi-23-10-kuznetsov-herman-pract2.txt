3 ОПИС ВИКОНАНОЇ РОБОТИ
      3.1 Загальні відомості про систему
      Назва системи: Google Drive
      Розробник: Google LLC
      Призначення системи: Хмарне сховище даних, що дозволяє користувачам зберігати файли на серверах, синхронізувати їх між пристроями та ділитися ними. Включає інструменти для спільного редагування документів у реальному часі.
      3.2 Архітектурний стиль системи
      Google Drive базується на мікросервісній архітектурі з використанням стилю Event-Driven (подієво-орієнтований) для синхронізації та Layered (шарової) архітектури на рівні окремих вузлів.
      Обґрунтування: Мікросервіси дозволяють незалежно масштабувати компоненти (наприклад, окремо сервіс перетворення відео та сервіс пошуку). Подієва модель необхідна для миттєвого сповіщення клієнтів про зміни у файлах.
      3.3 Основні компоненти системи
      Load Balancer: Розподіляє запити мільярдів користувачів між дата-центрами.
      API Servers: Обробляють запити на аутентифікацію та метадані.
      Block Servers: Керують завантаженням/скачуванням файлів, розбиваючи їх на блоки (chunks).
      Metadata DB: Зберігає інформацію про назви файлів, версії, права доступу (використовується Google Spanner).
      Block Storage: Фізичне сховище (Google Cloud Storage / Colossus).
      Notification Service: Надсилає пуш-повідомлення про зміни через WebSockets.
      3.4 Взаємодія компонентів
      При оновленні файлу:
      Клієнт надсилає запит до API Server.
      Файл розбивається на блоки, які передаються до Block Servers.
      Після успішного запису блоків у сховище, оновлюються метадані у Metadata DB.
      Notification Service надсилає сигнал іншим пристроям користувача про необхідність синхронізації.

Рисунок 1 -діаграма протоколів взаємодій
Опис протоколів взаємодії:
• HTTPS (TLS 1.3): Використовується як основний протокол для зовнішньої комунікації між клієнтом (браузер, мобільний додаток) та API Gateway. Весь трафік шифрується за допомогою сучасних стандартів TLS, що забезпечує конфіденційність метаданих та самих файлів при передачі через відкриті мережі.
• gRPC (Google Remote Procedure Call): Застосовується для внутрішньої взаємодії між мікросервісами всередині дата-центрів Google. gRPC використовує Protocol Buffers (Protobuf) як формат серіалізації, що значно швидше за JSON. Це дозволяє мікросервісам (наприклад, сервісу прав доступу та сервісу метаданих) обмінюватися даними з мінімальними затримками.
• WebSockets: Цей протокол забезпечує постійне двостороннє з'єднання між клієнтом та Notification Service. Саме завдяки WebSockets реалізовано механізм "push": коли файл оновлюється на сервері, клієнт миттєво отримує сигнал про необхідність синхронізації без постійного опитування сервера (polling).
• Binary Stream (Over HTTP/2): Використовується Block Servers для завантаження та скачування частин (chunks) файлів. Використання HTTP/2 дозволяє мультиплексувати декілька потоків даних в одному з'єднанні, що прискорює завантаження великих папок.
• QUIC / UDP: Google активно впроваджує протокол QUIC для зменшення часу встановлення з'єднання (handshake) та кращої роботи в умовах нестабільного мобільного інтернету, що критично для мобільних користувачів Google Drive.
      Механізм обробки запиту:
1. Клієнт ініціює HTTPS запит на завантаження.
2. Load Balancer термінує TLS-з'єднання та перенаправляє запит.
3. Сервіси всередині мережі спілкуються через gRPC.
4. Після завершення операції, Notification Service через відкритий WebSocket відправляє підтвердження іншим пристроям користувача.
Ось детальний опис окремого пункту звіту, присвяченого потокам даних у Google Drive. Цей розділ пояснює логіку "руху" інформації всередині системи.
3.5 Діаграма потоків даних 
Діаграма потоків даних ілюструє життєвий цикл інформації в Google Drive: від моменту ініціації запиту користувачем до фізичного збереження байтів на дисках та оновлення стану системи на всіх пристроях. В архітектурі Google Drive ключовим принципом є розділення потоку метаданих (інформація про файл) та потоку блоків даних (вміст файлу).

Рисунок 2 - Діаграма потоків даних
Опис основних потоків даних:
Вхідний потік запиту (Control Flow):
Користувач взаємодіє з інтерфейсом (UI), надсилаючи команду на завантаження або зміну файлу. Запит надходить на Load Balancer, який на основі географічного положення та поточного навантаження дата-центрів спрямовує його до найближчого вузла API Server. Тут відбувається перевірка прав доступу (ACL) та автентифікація через сервіс ідентифікації.
Потік обробки контенту (Data Ingestion Flow):
При завантаженні файлу він не передається як єдиний об'єкт. Block Server приймає вхідний бінарний потік і розбиває його на блоки (chunks) фіксованого розміру (зазвичай від 4 до 8 МБ). Для кожного блоку розраховується контрольна сума (хеш).
     Шлях бінарних даних: Блоки паралельно передаються до розподіленої файлової системи Colossus, де вони реплікуються (копіюються) у декількох примірниках для забезпечення відмовоїстійкості.
Шлях метаданих: Інформація про те, з яких блоків складається файл, їхня послідовність та хеш-суми, передається до бази даних Google Spanner.
Потік оновлення стану (Metadata Flow):
Після успішного запису всіх блоків у Colossus, Metadata Service фіксує транзакцію в Spanner. Це оновлює версію файлу, час останньої зміни та ієрархію папок. Завдяки синхронній реплікації Spanner, ці зміни стають миттєво доступними у всьому світі.
Потік сповіщень (Notification Flow):
Як тільки транзакція в базі даних метаданих завершена, генерується подія "File Updated". Ця подія надходить до Notification Service, який ідентифікує всі активні сесії даного користувача (інші вкладки браузера, смартфони, планшети) і через відкриті WebSockets надсилає їм короткий сигнал-інструкцію про необхідність синхронізації.
      
      3.6 Масштабованість та надійність

      В.1 Реалізація механізму розбиття файлів на блоки (Chunking)
      Запит до ШІ: Напиши на мові Java приклад сервісу для Google Drive, який приймає вхідний потік даних (InputStream) великого файлу та розбиває його на блоки фіксованого розміру (наприклад, 8 МБ). Для кожного блоку потрібно розрахувати контрольну суму (SHA-256) для перевірки цілісності на стороні сервера. 
         1  import java.io.*;
         2  import java.security.MessageDigest;
         3  import java.util.Base64;
         4  
         5  public class FileChunkingProvider {
         6      private static final int CHUNK_SIZE = 8 * 1024 * 1024; // Порція 8МБ
         7  
         8      public void uploadByChunks(File file) throws Exception {
         9          byte[] buffer = new byte[CHUNK_SIZE];
         10         try (InputStream is = new FileInputStream(file)) {
         11             int bytesRead;
         12             int sequenceNumber = 0;
         13             
         14             while ((bytesRead = is.read(buffer)) != -1) {
         15                 // Створення копії блоку, якщо він менший за CHUNK_SIZE (останній блок)
         16                 byte[] chunk = (bytesRead == CHUNK_SIZE) ? buffer : 
         17                                java.util.Arrays.copyOf(buffer, bytesRead);
         18                 
         19                 String checksum = calculateSHA256(chunk);
         20                 // Виклик методу відправки блоку на Block Server
         21                 sendToBlockServer(sequenceNumber++, chunk, checksum);
         22             }
         23         }
         24     }
         25  
         26     private String calculateSHA256(byte[] data) throws Exception {
         27         MessageDigest digest = MessageDigest.getInstance("SHA-256");
         28         byte[] hash = digest.digest(data);
         29         return Base64.getEncoder().encodeToString(hash);
         30     }
         31     
         32     private void sendToBlockServer(int seq, byte[] data, String hash) {
         33         // Логіка передачі даних через gRPC або HTTP до сховища Colossus
         34         System.out.println("Uploading chunk #" + seq + " with hash: " + hash);
         35     }
